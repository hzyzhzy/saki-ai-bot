> **这份文档给"以后想复用 / 接手 / 判断能不能用它"的人看。**
> 放在 `tools/` 里是因为**代码全在这一层**。
> 最后更新：**2026-11-21**
> 当前状态：**已停用，作为技术储备**（用户 2026-11-21：「把爱音也先接进 SL，关掉 anode 模式，
> anode 模式作为技术储备吧，关闭 anode 自启」）
>
> ⚠️⚡ **一句话说清为什么停用：太慢** —— 发一条文字约 **4 秒**、发一张图约 **20 秒**、

## 一、它是什么

anode（`<本机用户目录>\AppData\Local\Programs\Anode\`）是**一台虚拟桌面的席位**。
我们用它跑一个**独立的 QQ 客户端**，然后靠 **UIA（Windows 辅助功能）读屏 + 模拟鼠标键盘**，
把它包装成一个**假的 OneBot 服务端** —— 这样 bot 完全不知道自己在和一个"读屏机器人"打交道。

```
   bot（真 OneBot 客户端）
        │  ws://127.0.0.1:6700
        ▼
   tools/qq-onebot.mjs        ← 假 OneBot 服务端（**适配器**）
        │  ▲ HTTP 6701
        │  │ 推送
        │  └──────────────┐
        ▼                 │
   tools/qq-py.py     tools/qq-daemon.py    ← 读屏（**daemon**）
   （发送：切群/打字/点按钮）      ▲
                                │ UIA
                                ▼
                       座位里的 QQ.exe（anode 虚拟桌面）
```

## 三、缺陷（**这些是它被停用的原因，也是复用前必须知道的**）

### 3.1 🔴 私聊完全不行

daemon 只切**群**、不切私聊 ⇒ 私聊**读不到也发不出**。
（`qq-py.py` 的 `do_switch` 是按会话名匹配，但 daemon 的主循环只遍历群。）

### 3.2 🔴 表情格式做不到（**硬边界**）

QQ 里「表情消息」和「图片消息」是**两种不同的消息元素**（`market-face` vs `pic-element`）。
客户端走 UI 只有两个入口：

- 点「**图片**」按钮 ⇒ 必然生成 `pic-element`（**永远是图片**，转成动图也一样）
- 点「**表情**」面板 ⇒ 面板里只有 **QQ 服务器上你账号的表情库**，我们的 `library/` 是本地文件夹，两边不通

实测 `qq-read.py` 读回来是 `kind='image'`，即便源文件是 47 帧的动图 GIF ✗

### 3.3 🔴 拿不到图片原图

`get_cookies` / 读取 QQ 本地图片缓存 → **物理做不到**。图片只能**按屏幕矩形裁屏**，
分辨率取决于座位分辨率（1920×1080）。QQ 窗口被遮挡 / 滚动出视口 ⇒ `rect[1] < 0` ⇒ 截不到。

### 3.4 🟡 座位不是常驻服务

`anode status` 报 `Anode is not running` = **整个座位没了**（QQ / daemon 全死）。
租约 `--ttl 600` 最长 10 分钟，`anode display` 绑租约（到点分辨率回落）。
座位 session 号会变（见过 2 和 3），**别硬编码**。

### 3.5 🟡 daemon 是"读屏"，本质脆弱

- **一卡就全停**：2026-11-21 因为 `POKE_SEEN` 从 `set` 改成 `dict` 漏了 `.add()`，
  每轮读消息抛异常 ⇒ **推送数停在 21 再也不涨** ⇒ 她一条都收不到，而日志里只一行报错。
- **只能读当前会话**：daemon 必须来回切群才能读到各群消息，切一次 600~1300ms。
- **消息排队会丢**：实测出现「排队已经攒到 3 条（阈值 3 条）→ **丢掉排队中的消息**」。

### 3.6 🟡 群名是唯一索引（串群风险，已修但要知道）

`state/qq-seen.jsonl` 里存的是**群名**（不是群号）。`get_group_msg_history` 原来写的是：

```js
if (wantName && String(o.g) !== wantName) continue;   // ← wantName 为空时整条不成立 = 不过滤
```

⇒ 群名映射没建立时（新群 / 映射丢了）会**返回所有群混在一起的记录** ✗
（实测 `group_id=999999999` 这个不存在的群也返回 50 条）

**已修**：映射不到就**返回空**（宁可查不到，绝不给错的）。

### 3.7 🟡 cmd 传参会被拆

群名带**空格 / 方括号**时（如 `[示例服务器外群] 示例群`），
通过 `anode exec -- cmd /c "... --group [xxx] yyy"` 传会**被拆成两个参数**，
目标变成 `H`，而 header 校验因为"包含关系"**通过**了 ⇒ 切到私聊「H」✗

**绕法**：把参数写死在临时 .py 脚本里，别从命令行传。

### 3.8 🟡 发图会发到"当前会话"（已修）

`qq-send-image.py` 原来**只往当前打开的会话发图、不切群**，
而 daemon 一直在后台按需切群 ⇒ 图会落到 daemon 当时切过去的那个群 ✗

**已修**：加 `--group`，先切群、发之前**再验一次 `chat-header`**，对不上直接 exit 9 不发。

### 3.9 🔴🔴 **耗时太长（这是被停用的主因之一）**

**用户原话（2026-11-21）**：「**还有耗时太长也写进去**」。

#### 硬数字（都实测过，不是估算）

| 操作 | anode 客户端模式 | SL | 差多少 |
| --- | --- | --- | --- |
| **发一条文字** | **约 4 秒** | 几十毫秒 | **100 倍** |
| 引用 + 发一条 | **约 12 秒** | 几十毫秒 | 300 倍 |
| **发一张图** | **约 20 秒** | 几百毫秒 | 50~100 倍 |
| 读一条消息 | 读屏一轮 0.3~1.3 秒 | 事件推送 | — |
| 切一次群 | **600~1300 ms** | 不需要 | — |

#### 4 秒是怎么花掉的（`qq-py.py` 内部计时，实测）

```
找输入框        80 ms
聚焦             2 ms
清空输入框      529 ms   ← 逐字删 / Ctrl+A+Delete 都要走 UI
逐字输入        954 ms   ← 必须逐字 SendUnicodeChar（整串会吞字、重复）
找发送按钮      530 ms
点发送          ~不等验证
─────────────────────
合计            ~2.4 秒（这是"已经在目标群"的情况）
+ 切群握手      1~1.5 秒（daemon 替发送方切，或自己切）
─────────────────────
实际一条        ~4 秒
```

⚠️ **为什么不能更快**（都试过，别再走回头路）：
- 整串 `SendKeys` ⇒ **吞字 / 重复 / 清不干净**，只能逐字
- 不逐字前确认焦点 ⇒ `SendUnicodeChar` 返回非 0 但**框是空的**（假成功）
- 清空必须真的清（`Ctrl+A` + `Delete`），否则残留会和正文粘一起

#### 对体验的实际影响

- **说话要等 4 秒才出现在群里** —— 她能"想"得很快，但发不出去
- 一连发 3 条 = **12 秒**，中间别人早就插话了
- 发图 20 秒 ⇒ 用户早就问"图呢？"
- 她自己也会被这个卡住：`sendChunk` 是串行的，第 2 条要等第 1 条发完

#### 更糟的是：**慢会引发连锁**

daemon 读屏是"切群 → 读 → 推"的循环，而切一次群要 600~1300ms。
群一多，一轮要好几秒 ⇒ **消息延迟累积**，而且实测出现过：

```
排队已经攒到 3 条（阈值 3 条）→ **丢掉排队中的消息**
```

⇒ 不只是"慢"，**慢到一定程度会直接丢消息** ✗

### 3.10 🟡 发送是串行的，一条堵全堵

`qq-py.py` 走 `withLock`（同一时刻只允许一个发送），而发图要 20 秒 ⇒
**发图期间她完全发不出文字**。

## 四、如果以后要重新启用（检查清单）

### 4.1 起链路（**别用 `start-saki.ps1`，那个是老的**）

```powershell
# 现在要手动按顺序起（2026-11-21 起 SL 是正路，anode 只作储备）
cd '<项目目录>\qq-ai-bot'

# ① 席位（必须）
anode start --hidden
anode status                       # 要 state=ready

# ② 租约（10 分钟，会过期）
$t = (anode --agent dsh lease acquire --ttl 600 | Select-String 'leaseToken').Line -replace '.*"leaseToken": "([^"]+)".*','$1'

# ③ 座位里的 QQ（认昵称 → 点登录）
anode --agent dsh --lease $t exec --cwd C:\Temp --timeout 120000 -- cmd /c "C:\Temp\dbenv\Scripts\python.exe <项目>\tools\qq-seat-boot.py"

# ④ 适配器（零窗口）
wscript.exe "tools\启动适配器（隐藏）.vbs"    # 带 --port 6700 --self <QQ>

# ⑤ daemon（零窗口，**--me 必须是座位里登的那个号**）
anode --agent dsh --lease $t run wscript.exe "<项目>\tools\_daemon-hidden.vbs"

# ⑥ bot 的 onebot.url 指回 6700
```

### 4.2 换号时**必须一起改**的 5 处

| 改什么 | 在哪 |
| --- | --- |
| bot 连哪个端口 | `accounts\<QQ>.yml` 的 `onebot.url` |
| 适配器认自己是哪个号 | `启动适配器（隐藏）.vbs` 的 `--self` |
| daemon 认谁是"自己" | `_daemon-hidden.vbs` 的 `--me`（**不改会把她自己的话当别人的推回来**）|
| SL 别碰这个号 | `C:\SnowLuma\config\runtime.json` 的 `uinWhitelist` |
| 座位里登哪个号 | 手动（QQ 客户端）|

### 4.3 改完**必须**验的七段（AGENTS 里也有）

```
① daemon 落盘       logs/qq-daemon.log 有「落盘 N 条」且没报错
② 推送数在涨         心跳行 推送=N，隔一会儿要变大（不涨=卡了）
③ 适配器收到         logs/qq-onebot.log 有「daemon 推了 N 条」
④ bot 收到           logs/bot-<日期>-<号>.log 有 [收到]
⑤ 说话判定跑过        [主动接话] 判定返回 / [group:xxx] at <-
⑥ 真的生成了         拼提示词 …（N 字） + 已回复 N 字
⑦ 真的发出去了        适配器 ✅ 已发出 message_id=…
```

⚠️ **「daemon 起来了」≠「能用」** —— 必须看到 ⑥⑦。
⚠️ 测试消息**只在用户批准的群发**（当前 `200000007`）。

## 五、和 SL 的对比（为什么现在走 SL）

| | anode 客户端模式 | SnowLuma |
| --- | --- | --- |
| 发送延迟 | **4 秒**（发图 20 秒） | **几十毫秒** |
| 表情格式 | ❌ 只能是图片 | ✅ `sub_type:1` 能发真表情 |
| 图片原图 | ❌ 只能裁屏 | ✅ 能拿原图 |
| 私聊 | ❌ 不支持 | ✅ |
| 引用发送 | ⚠️ 能做（右键气泡）但 12 秒 | ✅ 原生 |
| 依赖 | 座位 + QQ 客户端 + UIA（脆弱） | 只依赖 hook |
| 账号风险 | 同号两处登录会被踢 | 一个号只在一处 |

**结论**：功能上 SL 全面胜出；anode 的价值在于**"当 SL 完全不能用时的最后一条路"**——
因为它**不注入 QQ**（纯读屏），所以**QQ 大版本更新导致 native hook 挂掉时，它反而可能还活着**。

## 六、当时为什么上 anode（背景，避免重复决策）

2026-11-21 之前，Saki 走 SL、Anon 也走 SL，但**同一个号在 SL 和 QQ 客户端两边登**，
腾讯按多端处理**把客户端踢下线** ⇒ 用户原话：「先把 anode 模式交给 anon 吧，
saki 作为主号不能总是不能用」。

后来（2026-11-21 晚）SL 换到 v2.4.2 且**白名单/注入前探测补回来了**，
多号共存的问题有解了 ⇒ 用户决定**爱音也回 SL，anode 停用作储备**。
