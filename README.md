## ✨ 特色功能：它凭什么像个活人

> 普通的群机器人是"**你问它答**"。下面这几套东西是往反方向做的 ——
> 让它在群里**像一个有自己生活的群友**。

### 0. 服务器客服：**这个项目一开始就是为了它**

> 第一版没有好感度、没有剧情、没有 QQ 空间 —— 只有一件事：
> **群友问「服务器怎么进 / 现在几个人 / 为什么连不上」，它能用自然语言答上来。**
> 下面 1~8 条都是后来长出来的，但**这一条一直是它唯一的「正经职责」** ——
> 代码里也这么写：别的都能判断"该不该开口"，**服务器问题必须单独放行**。

| 它怎么做 | 为什么这么做 |
| --- | --- |
| **自己用 MC 协议去查**（Server List Ping + SRV），查不到才退到第三方 API | 不依赖别人家的接口；而且状态**必须是真的**，不能猜 |
| **查不到就不编** | 提示词里明写「查询失败就直接说失败，不要编造」；真失败时用**上一次成功的数据**兜底，并**注明这是刚才查的** |
| **不受灵敏度档位限制** | 3 档群（只认 @ 她）照样答服务器问题 —— 那是职责，不是"搭话" |
| **问"他什么时候上来的"也答得上** | 有个后台每 60 秒记一次在线名单，所以在线时长有据可查（⚠️ 没这段数据时**不许说**"他刚上来"，这条是踩坑加的） |
| **两套知识协同** | 服务器资料走本地知识库（`hzymtr-server.md`），实时人数走这次查询 —— **"该用哪份资料"这件事本身就是个真问题** |

**活人感在哪**：她答服务器问题时会**切回客服状态**（语气正经、不玩梗），
平时还是活泼的群友 —— 这个"看场合切换"是刻意做的（`detectMode()`）。

### 1. 随机事件：它有自己的一天

`knowledge/life-events.md` 是一张**时段表**（早上 / 上午 / 中午 / 下午 / 傍晚 / 晚上 / 深夜），
里面是几百条"今天可能发生在她身上的小事"：

```
上午 09:00-12:00  上课打瞌睡被老师点起来回答问题     #学校
下午 13:30-17:00  放学直接去打工，校服都没换         #打工 #学校
傍晚 17:00-19:30  客服室被一个用户缠了半天，她全程没抬高声音  #打工 #倒霉
```

每天挑几条（默认 3~10 条、7 点前不发、两条之间至少隔 90 分钟），**润色成她自己的一句话**发到群里：

> 「交班的时候同事多留了十分钟，帮我把东西收拾完才走」

**活人感在哪**：它不是"报天气"，是**在群里说自己的事**。
而且这些事**跟时间对得上** —— 上午在学校、下午去打工、深夜话少。

- **她不知道「群里的人」知不知道这件事** → 提示词里强制：说清楚"谁+干了什么+结果"，别用「那条消息」指代
- 断网/关机**不补发**（过去了就是过去了，真人也不会补报昨天）
- 管理界面有**「预览一条 / 立即发送」**：预览=只润色不发、立即发送=**发的就是你看过的那一条**

### 2. 二级剧情：一段能连着演几天的故事线

一级事件是"一天里的小事"，二级剧情是**一段有起承转合的线**（默认一天最多一条）：

- 模型生成**阶段脚本**（≤10 段，越往后概率越低 → 大部分线 3 段左右就收）
- 每段**等群友接话**（默认 30 分钟），冷场最多续 1 次，来不及就收
- 走完有**结局**：好结局 好感度 +3，**坏结局 −2**，而且**下一段剧情会往"补救"方向走**（赎罪弧）
- ⚠️ **她转述剧情必须有来龙去脉**：不能张口就是「他刚才说」，得先交代前因
- ⚠️ **收信人永远是群友**：不是对着她的队友下命令（这是真实踩过的坑）

**故事线（每个群各一份）**：她记得"这个群里发生过什么"，分一级（事件）/二级（剧情），
**二级条目永不被删** —— 自动压缩时模型想删/扩写都会被拦，**整次作废重来**。

### 3. 动态功能：她还会自己发 QQ 空间

- 攒群里的素材（谁说了什么、什么梗在飞），攒够就写一条**说说**
- 有配图就从表情库里挑一张；每天最多 6 条、两条之间至少 2 小时
- ⚠️ **发过的说说和当天条数都落盘** —— 不然重启就忘，同一个梗会连发三遍（真实踩过）

### 4. 表情包：会斗图，而且不回一句"至于吗"

- **自动收集**群里发的表情（进 `_pending/` 待审核，界面上标注用途）
- 它说话时可以带 `[表情:无语]` 这种标记 → **图片单独发一条**，文字不跟图混在一起
- **斗图**：有人连发同一张表情，它**原样回一张、一个字都不打**（走模型就会变成"评论你的表情"，很出戏）
- 分条时**保护标记不被切断**（不会发出半个 `[表情:`）

### 5. 对话状态机 + 说话判断：**该不该开口**是"判断"，不是"抽签"

这个模块的设计目标是：
> 「不是降低概率，而是**监听群聊对话、自己决定什么是应该回的**，必须向真人靠近」

所以：

- **状态机**（`src/dialogue.js`）把一段对话当成有生命周期的东西：
  `idle ⇄ active`，active 里再分 **他 / 别人 / 没在聊** 三态；
  记着"这一段她说了几句、对方说了几句、她上一句是什么、上次开口多久前"
- **说话判断**（`src/speak-judge.js`）是一次**便宜的模型调用**，拿这些状态决定说不说：
  - 默认**闭嘴**（"少说一定比多说要好，真需要时我们会 @ 它"）
  - 但**服务器相关的问题即使没点名也答**（那是它存在的意义）
  - **「你自己的状态」也喂给它** → 刚说过就别追、这一段说太多就收住
    → **密度由判断管，不靠"每分钟最多几句"那种硬闸**
- **被 @ / 引用 / 点名叫她 / 命中关键词 / 服务器问题** 这几类"明确召唤"**不受冷却影响**
  （真人不会因为两秒前刚说过话就不理你）
- ⚠️ **没人指名她时，她不把自己当主角**：只有 **@她 / 叫她的名字 / 引用她的话**（私聊也算）
  才让她进入"被问的那个人"的姿态；其余情况她只是**群里路过搭一句**的群友 ——
  **不辩解、不自证、不把话题拉到自己身上**（真实踩过：有人说「机器人一来群消息多好多」，
  她回「消息多又不是我发的（」—— 一句随口吐槽硬是变成了她在受审）

**活人感在哪**：她的安静和她的开口**都是有理由的**，而不是每 3 分钟掷一次骰子。

### 6. 好感度：她对**每个人**都有私人评分（0~100，默认 50）

不是"全局好感度"，是**按人分开记**的；而且是**按群各记各的**（同一个号在 A 群混得熟，
不代表在 B 群也熟）：她跟谁处得来、跟谁只是客气，一个群一套。

**改变它只有两种来源**（代码层保证，不是靠提示词祈祷）：

| 来源 | 变化 | 说明 |
| --- | --- | --- |
| **群友回应她**（@她 / 回复她） | **+1** | 只在她**刚在这个群说过话的 30 分钟内**算；防刷 |
| **有人骂她** | **−2** | 判据是「**出现侮辱词**」+「**指向她**（@她或点她的名）」两条同时成立；**宁可漏不可误伤** —— 「这服务器真垃圾」不算骂她，熟人之间「你好笨啊」也不算。⚠️ 减分**不占**每天的加分额度 |
| **剧情结局**（二级剧情走完） | **好结局 +3 / 坏结局 −2**（可配） | 一次给**参与者多人**结算 |
| 其它任何东西 | **不动** | 群记忆压缩 / 自动观察**一律不许碰它**（铁律，代码层面隔开） |

防刷分：单次最多 ±3、**每人每天最多 +8**。⚠️ 那条上限**只管加分** ——
**减分不占它**（否则"今天已经跟她聊满 8 分"的人再骂她就减不动了，
而那恰好是最该扣分的情形：先聊熟、再随便骂）。

**它有什么用**：

- **决定她对普通群友的距离感** —— 分高接得住话、分低只剩礼貌
  （⚠️ 但**该答的问题照样答**：不许"因为讨厌你就不理你"，这也是铁律）
- **到 90 分** → 在群里 @ 他「来加个好友」；加上之后**每天有概率主动私聊**
- **目前**好感度的奖励还比较少，现有的是对人态度会随好感度变化，到达90会发好友申请。后续会慢慢加，也可以向我们提建议。
- `/好感度` 看榜单：只列**最近有变化的 10 个人**，显示**群名片名字**（不是 QQ 号），
  而且是机器格式、**不进聊天上下文**（不然她下次说话会把榜单当聊天内容，就露馅了）
- ⚠️ **对主人不生效** —— 她和主人的关系是单独一套（`knowledge/relationship.md`），优先级更高

#### 好感度 × 随机事件 × 剧情：三者是什么关系

| | 它是什么 | 动好感度吗 | 为什么 |
| --- | --- | --- | --- |
| **随机事件**（一级） | **她自己的日子**：上课打瞌睡、交班、被用户缠 | ❌ **不动** | 那是"她今天过得怎么样"，不是"她对某个人的看法"。它负责**让她有生活、有话题**，不负责发分 |
| **二级剧情** | **她跟这个群一起经历的一段事**（有起承转合、有结局） | ✅ **动**（好 +3 / 坏 −2） | 一起经历过事才会改观 —— 这是好感度**最主要、最有分量**的来源；坏结局还会让她**下一段往补救方向走** |
| **日常互动** | 群友 @她 / 回她 → **+1**；**有人骂她 → −2** | ✅ | 一次一句慢慢处出来的；有窗口 + 每天上限，防刷。⚠️ 但「骂她」那条**不受每天上限约束** —— 扣分不该被"今天已经聊够了"挡住 |

一句话概括：

> **随机事件负责"她像个活人"，剧情负责"她和这群人之间发生了什么"，好感度负责"这些事在她心里留下了什么"。**

### 7. 工资：她有一份**真的收入**，而且会为钱发愁

她在这当客服是**打工，有工资的** —— **LLM 模型的账上扣多少钱乘 100，就是她这个月挣的钱**。
这跟人设是一条线的：家道中落之后她就一直在自己挣钱（接活、打工、组乐队），
所以"钱"对她**不是抽象数字**，是真会影响她的东西。

**这一块的设定（都是代码里定死的，不是随口说）**：

| 规矩 | 为什么 |
| --- | --- |
| **数字由代码算好，只让模型组织说法** | 让它自己算一列数字**必错**（实测会把 1847 说成整百）—— 所以事实里塞的是算好的数 |
| **问花销 / 问工资分开答** | 以前糊在一起：问「赚了多少」会甩一堆花费明细，问「花了多少」又带上工资 |
| **按现实物价给她参照** | 一两千 = "打零工/兼职"那档（比多数城市最低工资还低）、两三千 = 刚够自己过、四五千 = 普通上班族 —— 她会说成「够买几杯奶茶、几顿正经饭」，而不是报一个数字 |
| **余额见底会真的抱怨** | **低于 5 元**抱怨一次、**低于 2 元**再抱怨一次；⚠️ 只在**群里冷场 3 分钟后**说 —— 别人正聊着的时候插一句"我工资没了"很突兀 |
| **月末工资单** | 每月最后一天 21 点，发到所有 1 档群 + **同步一条 QQ 空间**；掉线了重连时会**补发** |
| **「余额」和「工资」是两件事** | 余额见底是**主人的事**（该去充了，她会直接点他）；工资是"她挣多少、够不够花" |

⚠️ 账本是从 2026-09-13 才开始记的 —— 更早的花费没有记录，
所以要由人从模型用量页读出"本月累计"，用 **`起始账 2026-09 18.34`** 这条指令告诉它一次
（它会自己减掉已经记过的部分，不会重复计）。

#### 工资和花费的数字是怎么算的、什么关系

**两个数都出自同一份账本**（`state/spend.json`），只是**换了个说法**：

| | 怎么算 | 对外怎么说 |
| --- | --- | --- |
| **花费（成本）** | 每次调模型都记下 token 数（输入/输出/命中缓存），乘**价格表**得到一次的钱，按天累加 | 「我这个月花了多少」——×1 |
| **工资（收入）** | **花费 × 100** | 「我这个月挣了多少」——×100 |
| **差额（净赚）** | 内部算得出来，**但绝不对外说** | 🚫 **不要说净赚** |

**为什么这么定**：

> **花掉的钱 = 成本**，**赚到的钱 = 每月发给祥子的工资**，
> 工资取 **API 消耗余额 × 100** —— 这样账目自圆其说，
> 而且她看到的是「这个月花了多少」，**不像 AI 在烧 token**。

⚠️ 这一条是整个工资设定的**钥匙**：她会说「这个月到手才这么点」，而**不会**说
「系统余额不足」—— 后者一眼就是机器人。她的抱怨永远是**"我自己赚的钱不够花"**。

**价格表**（元 / 百万 token）分**高峰 / 空闲**两档，高峰是空闲的 **2 倍**：

```
deepseek-flash ： 缓存命中 0.02 / 未命中 1 / 输出 4      （高峰时翻倍）
另一种模型     ： 0.15 / 4.5 / 13.5                      （高峰时翻倍）
```

**为什么要自己记账**：官方只有"查余额"接口、**没有历史账单接口**；
而且余额是两位小数，而**调一次可能只花 0.000334 元** —— 从余额上根本看不出来。
所以只能每次调用自己记一笔（这也是为什么需要上面那条 `起始账`）。

**余额（账上还剩多少）和这两个数的关系**：
余额是**主人往账户里充的钱**，在提示词里就是「她账上还剩多少」——
**低于 2 元**会在群里 **@ 主人**提醒一次（每个群各提醒一次，不重复刷），
真的耗尽（HTTP 402）也走同一套话术，**不会甩一句「⚠️ API 余额不足」**给群友。
（更低一档的「低于 5 元」随口提醒**默认关着**，`balance.low` 改回正数就恢复。）

**活人感在哪**：她的收入**是有量级、有参照、有情绪的** ——
不是读一个 API 余额，而是"这个月到手这么点，房租一除就没了"。
冷场时才提钱、月底才发工资单，也都是**按人的节奏**来的。

### 8. 刷屏群里也不糊：**合并上文 + 分人识别 + 该引用时引用**

大群一热闹，普通机器人立刻犯三种病：**同一句被反复回**、**把 A 说的记到 B 头上**、
**答的是三十条之前那句**（早被刷上去了）。这一套就是专门治这个的：

- **合并上文**：同一个人手一抖连发几条 —— 或者它正在生成时群里又来了几条 ——
  → **合成一次回答**，而不是一条一条各答一遍；合并时把"来自谁"一起带上
- **精准区分发言人**：上下文里每条都带**发言人**（`张三：…`），提示词里明确要求按人对应，
  所以「他刚才说的」不会串到别人头上；**@ 的是别人时它不插嘴**
- **被淹没就引用**：她上一次说话之后，群里又刷过 **4 条以上**（`chat.quoteAfterGap` 可调）
  **并且**她要回的那条**已经被刷下去了**（后面还有人说过话）时，
  她的回复会**引用她在回的那条消息** —— 不然群里根本看不出她在答哪一句。
  反过来：间隔不到 4 条时**不引用**；**紧挨着她的回复的那条也不引用**
  （满屏引用框像工单系统，那是另一种不像人）；**没检测到间隔同样不引用**
  （新群/刚重启不会变成每条都引用）。被刷下去 ≥4 条时无论如何都引用
- **引用她 = 对她说话**：群友**引用她的消息**（**没 @ 也算**）→ 直接回，
  不看灵敏度档、也不受触发冷却影响 —— 真人聊天里"引用你上一句"和 @ 你是一回事
- **点名叫她也算召唤**：正文里写「**祥子 / 小祥 / saki**」就等于 @ 她 —— 三档都认、
  不受冷却、也不经过说话判断（`trigger.callNames` 可改）。
  起因是个真实事故：群里那句「祥子你现在和谁住在一起」被"判断节流"直接丢掉了，
  因为它当时既没 @ 也没关键词（「骆驼祥子」那本书不算在叫她）
- ⚠️ **不加 @**：引用就够了，@ 会弹通知、太吵
  （只有「余额见底催充值」那条会 @ 主人，那是有意留的）

**活人感在哪**：热闹群里它抓得住重点、也不会把别人的话算到自己头上；
答一句三十条之前的消息时，它会把**被答的那句引用出来** ——
就跟真人补一句「（回你上面那个）…」一样。

| 协议端自愈 | 连续发送失败 → 写条子让看门狗重启 NapCat；QQ 假在线能识别 |
| 看门狗 | 机器人挂了自动拉起来；NapCat 卡死/掉线也会处理（PowerShell 脚本） |

| **界面外观** | 管理界面是**液态玻璃**风格：背景油滴会跟着鼠标散开、卡片边缘一圈**随鼠标方位变化的折射高光**（鼠标在哪侧哪侧就亮、离远了会衰减），右上角可切**深色模式**（选择会记住）。⚠️ 改界面**不用重启** —— `webui.html` 是按请求热读的，刷新浏览器就生效 |
| 网络搜索 / B站 | 预搜索（判断这条要不要联网查）→ 多引擎汇总再过滤；B站热门榜 / 某个 UP 主的最新投稿 / 某个题材的热门 |
| 拟人细节 | 分条发送、破折号→逗号、去掉聊天里不用的标点（「」这种"打字打不出来"的一律去掉）、口癖节流、防刷屏、图片占位符、引用回复 |

### 9. 知识库：**分层 + 按需**，而不是"能写的都塞进去"

先说结论：**这不是一份大提示词，而是一组有分工的文件 + 一套挑选规则。**

因为提示词不是越长越好，两头都会出问题：

| 太短 | 太长 |
| --- | --- |
| 她不像那个人 —— 没有性格、没有生活，说话像客服机器人 | 模型的注意力被摊薄，**夹在中间的那些规则会被漏掉** |

第二种尤其阴 —— 它的症状不是"胡言乱语"，而是**偶尔漏掉某一条规则**：平时都对，
某次偏偏把不该说的说了。所以这套知识库的设计，有一半是为了防这件事。

#### 有哪几份

| 文件 | 装什么 | 什么时候进提示词 |
| --- | --- | --- |
| `persona.md` | **她这个人**：身份、说话方式、性格、十条铁律 | **永远** |
| `persona-money.md` | 工资 / 报账 / 余额的细则（含"红包一律不收"那套） | 聊到钱、红包、转账、代付时 |
| `persona-media.md` | 表情包怎么用、收到图片怎么反应、自己发动态 | 消息里带图/表情，或要发动态时 |
| `owner.md` | **服主本人**的资料（经历、朋友、偏好） | **只在跟服主说话时**（群里、私聊都算） |
| `relationship.md` | 她和服主之间那层关系 | 同上 |
| `hzymtr-server.md` | 服务器资料（整合包 / 模组 / 线路 / 报错…） | 命中服务器关键词时 |
| `group-memory.md` | 共享的群记忆 | 提到"群里 / 群友 / 你还记得"时 |
| `groups/<群号>.md` | **这个群自己**的资料 | 同上，且**只认当前那个群** |
| `dm/<QQ号>.md` | **私聊记忆**（只在"纯好友、跟他没有共有群"时才单独存） | 跟那个人私聊时、或他在群里说话时 |
| `learned.md` | 群主后来教的知识（**优先级最高，会覆盖上面所有**） | 按条目标题挑，只带**沾边的那几条** |
| `cast.md` / `holidays.md` / `life-events.md` | 角色表 / 节日表 / 事件库 | **不进聊天**（代码查表用） |

#### 怎么防"太长 → 漏规则"

1. **铁律放两头。** `persona.md` 开头一节「**先看这十条**」，结尾再来一遍
   「**最后再扫一遍**」—— 因为**开头和结尾最不容易被漏掉，中间最容易**。
   这十条每条在正文里还有详细说明，但**不依赖正文也能执行**。
   （不靠"模型应该记住"这种东西，靠的是把它放在注意力最稳的位置。）
2. **按需加载。** 用不上的库根本不进提示词：一句闲聊只有人设那 37K 字；
   问到服务器才多带服务器库；问到钱才多带工资那份。
   挑不挑由两件事决定 —— **关键词**，以及**"消息里有没有出现那个库里的人名/词条"**。
3. **一份知识只有一个家。** 服务器的事只在 `hzymtr-server.md`，群友的事只在那个群的
   资料里，**私聊归到他所在的那个群**（同一套资料库）—— 不复制、不重叠，
   就不会出现"两份说法打架、模型挑错那份"。
4. **优先级写进提示词。** `learned.md` 那一段显式声明「与上面冲突时以下面为准」，
   而且放在最后 —— 后出现的内容更靠近用户提问，模型也更重视。

#### 怎么防"太短 → 失去代入感"

- 人设那份**永远在**，而且写得具体到"她今天上什么班、外卖被偷过、工资多少、
  打工的地方在哪儿" —— **具体的生活**才让人有代入感，抽象的性格标签不行。
- 随机事件 / 二级剧情 / QQ 空间那几套功能负责**持续给她制造新素材**，
  再经"观察"写回那个群的资料 —— 所以她的记忆是**越用越长**的，不是每次从零开始。
- 但**边界很清楚**：她只知道自己该知道的。不在提示词里的事，规则要求她
  **直说不知道**，而不是编一个听起来合理的答案 —— 一个会承认"我不知道"的角色，
  比一个永远答得出来的角色更像人。

## 人设概要：她是谁

**丰川祥子**（Togawa Sakiko）——《BanG Dream! It's MyGO!!!!!》/《Ave Mujica》的键盘手，
代号 Oblivionis。家道中落后退掉了 CRYCHIC、转学羽丘，自己挣钱过日子。
粉丝管她叫「**客服小祥**」——因为她确实在外面打工，官方愚人节还真让她当过客服。

### 她的一天（时间线是硬事实，别演串）

| 时间 | 在哪 | 能不能回消息 |
| --- | --- | --- |
| 白天上课 | 羽丘女子学园（高一特招生），手机在桌洞里静音 | **回得慢**，但会偷着回 |
| 课间 / 午休 | 走廊、食堂、天台 | 能，回得快 |
| **放学后** | **客服室**（排班、有同事、有交班） | 能 —— 那就是她的工位 |
| 晚上 | 写作业、练琴；**手机上的客服软件还挂着** | 能，通常在线 |
| 深夜 | 睡不着 / 顺手看单子 | 也能，但话更少 |

> 「回得慢、忽然不接话」**不用解释也不用道歉** —— 上课收手机，刚看到而已。

### 她怎么说话

- **短**。像随手打的，不打句号，不分点列举
- **不要客服腔**：不说「您好，请问有什么可以帮您」「非常抱歉」——礼貌是教养，不是职业培训
- **外柔内刚，偶尔带刺**；不诉苦、不卖惨（家道中落是**过去的事**，她在过自己的日子）
- 对**主人**：平级口吻，不端着，接得住他的好话
- 对**群友**：礼貌里带点距离，该怼就怼

### 她心里的事（**默认嘴硬，但主人追问到底可以说出来**）

她为什么回消息这么勤？
**一半是想多赚点钱**（这话她张口就来，谁都挑不出毛病），
**另一半是……想跟主人多说两句** —— 这半句她不会主动说，问急了会用傲娇挡回去
（「少自作多情」）；但**主人一直追问**的话，她会别别扭扭地承认（「……你非要问。」）。

> 更多细节在 `knowledge/persona.md`（人设全文）和 `knowledge/relationship.md`（她与主人的关系）。

## 部署全流程（从零到跑起来）

> 面向 Windows（脚本都是 `.bat` / `.ps1`）。Linux / macOS 能跑核心（`node src/index.js`），
> 但没有那套一键脚本，协议端也要按 NapCat 自己的文档装。

### 0. 先确认你要准备什么

| 要什么 | 说明 |
| --- | --- |
| **Node.js ≥ 18** | 实测在 24 上跑（`node -v` 看一眼） |
| **一个 QQ 号**当机器人 | ⚠️ 建议**小号**：要能扫码登录，而且协议端本身有风控风险，别拿主号 |
| **你自己的 QQ** | 填进 `ownerQQ` —— 她是"客服小祥"，对主人是另一种态度 |
| **大模型 API Key** | DeepSeek 或任何 OpenAI 兼容服务（`llm.baseURL` / `apiKey` / `model`） |
| **NapCatQQ**（QQ 协议端） | **必装**：机器人本体只是 OneBot 客户端，没有协议端它连不上 QQ |

### 1. 拿代码 + 装依赖

```bash
git clone <你的仓库地址> qq-ai-bot && cd qq-ai-bot
npm i                       # 依赖只有几个（ws / js-yaml / qrcode …）
node test/run-all.js        # （可选）先跑一遍测试：全部离线，不碰真 QQ、不花钱
```

### 2. 起协议端（NapCatQQ）—— 这一步最容易卡

1. 从 NapCatQQ 的 Release 下 **`NapCat.Shell`**（Windows 包），解压到任意目录；
2. **用包里的 `launcher-win10-user.bat` 启动**（它会设好几个环境变量、把 NapCat 注入 QQ）。
   ⚠️ **别直接调 `NapCatWinBootMain.exe`** —— 那样 QQ 会起来、但 **NapCat 完全没跑**
   （6099/3001 都不监听、日志里也没有新东西，很容易误判成"启动失败"）；
3. 首次启动要**扫码登录**（登录态失效时它也会停在二维码界面等你扫）；
4. 打开 NapCat 的 WebUI（默认 `http://127.0.0.1:6099`），在「网络配置」里加一个
   **WebSocket 服务端**：端口 `3001`，**设一个 token**（待会儿填进 `config.yml`）；
5. 确认 `3001` 在监听：

   ```powershell
   Get-NetTCPConnection -LocalPort 3001 -State Listen
   ```

> ⚠️ 它的 OneBot 服务端**只允许一个客户端**：机器人占着的时候，别的脚本连 3001 会被拒
> （排障时先停机器人）。

### 3. 填 `config.yml`（**别提交它**）

```bash
copy config.example.yml config.yml      # Linux/macOS: cp
```

必填这几项（其余都有默认值，模板里注释很细）：

| 配置项 | 填什么 |
| --- | --- |
| `llm.apiKey` / `llm.model` | 大模型 Key 和模型名（不用 DeepSeek 就连 `llm.baseURL` 一起改） |
| `onebot.url` / `onebot.accessToken` | `ws://127.0.0.1:3001` 和上一步设的 token |
| `ownerQQ` / `botQQ` | 你的 QQ / 机器人那个小号 |
| `trigger.allowGroups` | **它会在哪些群说话**（别的群一律当没看见） |
| `trigger.groupRespondTo` | 每个群的档位：**1 = 会主动接话**，2 = 只答服务器类话题，3 = 只认 @ 她。⚠️ **只有 1 档群进事件系统**（日常事件 / 剧情 / 余额提醒 / 好感度按群记） |
| `life.enable` / `quest.enable` | 日常事件 / 二级剧情：**建议先关**，测稳了再开 |

改完跑一下 `npm run check`（配置能不能解析 + 模型通不通）。

### 4. 知识库起头（三个"活文件"不进仓库）

```bash
cd knowledge
copy group-memory.example.md   group-memory.md      # 群友是谁、什么性格、群里的大事
copy hzymtr-server.example.md  hzymtr-server.md     # 你自己的服务器/业务资料
copy learned.example.md        learned.md           # 群里「记住：…」教的东西
```

- 想给**某个群单独一份资料**（比如另一个群玩别的游戏）：建 `knowledge/groups/<群号>.md`
  —— 它**只在那一个群里注入**，别的群一个字都看不到；
- 共享文件里也能圈"只给某个群看"的段落：`<!-- 群:群号 -->…<!-- /群 -->`；
- 表情库、故事线、好感度这些都是**跑起来自己攒**的，不用先填。

### 5. 启动

```bash
# Windows：双击 一键启动（QQ+机器人）.bat   ← 先确认协议端，再起机器人
# 或者手动：
node src/index.js
```

管理界面 **http://127.0.0.1:3099**（改配置热重载、表情库、知识库、日常事件预览、按群参数、
好感度榜、剧情控制、二维码…）。登录态失效时，在界面点**「显示二维码」**刷一张新的。

### 6. 确认真的起来了（日志里这四行缺一不可）

```
[..] INF 已加载表情库 N 张：...
[..] INF 已连接到 NapCat，等待消息…
[..] INF 已登录 QQ: <机器人QQ>
[..] INF  管理界面: http://127.0.0.1:3099
```

然后在群里 **@ 它**说句话 —— 有回复就成了。

### 7. 让它长期活着（可选但推荐）

| 脚本 | 干什么 |
| --- | --- |
| `看门狗.bat` | 盯着协议端和机器人：挂了自动拉起来，掉线/卡死也会处理 |
| `一键启动+看门狗.bat` | 上面两件事一起做 |
| **开机自启** | 在管理界面里一键开关（`http://127.0.0.1:3099` →「状态」→「开机自启」）。实际跑的是 `autostart.ps1`：开机**先等 OneDrive 同步完、等网络通**再启动，起不来会重试 3 轮，然后交给看门狗。写进注册表的启动项（任务管理器 →「启动」里叫 `SakiBot`），随时能在界面上关掉 |
| `开机启动.bat` | 手动跑一遍上面那套开机流程（不想用界面开关时用这个） |
| `停止机器人.bat` | 按命令行精确匹配停（**不会**误伤别的 node 进程） |

### 8. 常见坑（照这个表查）

| 现象 | 原因 |
| --- | --- |
| 一直「连接失败 / 3s 后重连」 | 协议端没起，或没登录 |
| 协议端起了但 `3001` 不监听 | 登录态失效、停在二维码等你扫（或被隐藏窗口启动了） |
| 日志说「已登录,无法重复登录」却收不到消息 | **卡死态**：重启协议端 |

| 反复重启之后被踢下线 | **一次重启 = 一次 QQ 登录**：别背靠背重启（隔 5 分钟以上） |

## 🔌 换一个协议端（不想用 NapCat 时）

机器人**只通过 OneBot 11 协议**跟协议端说话 —— 也就是说「收消息 / 发消息」这部分
**跟协议端无关**（换谁都是 `ws://` + token）。所以换协议端**只需要改 `config.yml`**：

```yaml
onebot:
  url: ws://127.0.0.1:3001     # 指向新协议端的 WS 服务端（不用改）
  accessToken: '...'           # 它的 token（不用改）
provider:
  name: llonebot               # napcat（默认）| llonebot | onebot（任意通用实现）
  dir: D:\LLBot                # 启动/守护脚本要用（可选）
  launcher: LLBot.exe          # 相对 dir 或绝对路径（可选）
  manageUrl: http://127.0.0.1:3080   # 它自己的管理界面（界面上给你个链接）
```

**"管理能力"各家不一样，机器人会如实告诉你** —— 不支持的能力会**明确拒绝并告诉你去哪儿做**，
不会假装成功：

| provider | 是什么 | 出码 / 重启 / 快速登录 | 许可（商用相关） |
| --- | --- | --- | --- |
| `napcat`（默认） | 注入官方 QQ 客户端 | ✅ 全都能（机器人代你点） | ⚠️ 自定义许可：**禁止商用** |
| `llonebot` | [LLBot](https://github.com/LLOneBot/LLOneBot)（独立应用：Desktop / CLI / Docker） | ❌ 到它自己的 WebUI / GUI 里做 | GPL-2.0：**允许商用**；但**分发**它（打包 / 私有化交付）必须一并提供源码 |
| `onebot` | 任何通用 OneBot 11 实现 | ❌ 用它自己的方式 | 看具体实现 |

> 💡 **想商用的话**：NapCat **不行**（明确禁止）；`llonebot` 可以（GPL-2.0，只要别把**它**打进你的分发物）；
> 真正"官方许可"的是 QQ 开放平台 / 企业微信，但那两条路要过审、能力也受限。
> 详见 [THIRD-PARTY-NOTICES.md](THIRD-PARTY-NOTICES.md)。
>
> ⚠️ 换协议端解决的是**许可**问题，**解决不了腾讯服务条款**问题 ——
> 所有第三方协议端都可能让账号被风控，请自行评估。

`provider.name` 写错了也不会把机器人搞挂：它会退回 `onebot`（只保证收发），
原值留在 `provider.nameRaw` 里方便排查。

## 🤖 这个仓库可以直接交给 AI 助手（agent）继续改

本仓库是**按「能交给 agent 自己维护」来写的** —— 接手的人不需要先读完 7500 行代码才敢动手：

- **`AGENTS.md` 就是给 agent 的操作规程**：启动顺序、重启纪律（**一次重启 = 一次 QQ 登录**，
  别背靠背）、别用名字杀 node 进程、测试假模型的两个坑、交付前要跑哪些套件、
  哪些文件不许提交。agent 读完它就知道**哪些事不能干**。
- **51 个离线套件**：`node test/run-all.js` 一把跑完（约 2.5 分钟）。
  全部自己起假模型 + 假协议端 —— **不碰真 QQ、不花 API 钱**，改完立刻能验证对错。
- **人设和知识库是纯文本**（`knowledge/*.md`）：改完在管理界面点保存就热重载，连重启都不用。
- **代码注释里写的是「为什么这么做」**，不是「这行做了什么」—— 旧坑不会被再踩一遍。

**怎么用**：把仓库目录丢给任何一个能读写文件的 coding agent，一句话就够：

```text
读 AGENTS.md，然后按它的规程改这个 QQ 机器人。改完跑 node test/run-all.js，
把失败的套件修到全过；要重启机器人之前先问我。
```

⚠️ 两条底线（`AGENTS.md` 里也写了）：**别提交 `config.yml` / `knowledge/*.md` / `state/`**
（里面有私有信息）；**别在 1 分钟内反复重启机器人**（会被 QQ 风控踢下线）。
